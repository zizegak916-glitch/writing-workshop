# LINUX DO 旧话题续更稿（v0.3.0）

> 这是可直接回复到旧话题的正文，不是 README。原话题：<https://linux.do/t/2277200>

## 建议标题（如果需要另开话题）

隔了快一个月，Writing Workshop 把底层 Go 引擎换掉了，也能用自己的文本校准提示词了

## 正文

佬友们，我回来填坑了。

上次更新这个项目还是七月底：<https://linux.do/t/2277200>

当时网页能写、能管项目，也有一堆 Prompt Skill，但底下那套 Go 运行时还是沿着 fork 过来的结构继续改。后来越改越别扭——页面看起来已经是自己的产品，核心 Agent 却还依赖外部的 `agentcore` 和 `litellm`。文档写得再长，也绕不开这个问题。

所以这二十多天没有继续往页面上堆按钮，主要干了两件事。

第一件，是把当前 Go 运行时换成仓库里自己维护的实现。

现在消息、工具调用、上下文压缩、用量统计、子任务、模型协议和安全编辑都在 `internal/engine` 里。`go.mod` 和当前 Go import graph 里已经没有 `voocel/agentcore`、`voocel/litellm` 这两个运行时依赖。OpenAI Chat、Responses、Anthropic、Ollama 四套协议也有自己的适配和模拟契约测试。

这里我还是把话说准：项目最初确实 fork 自 `voocel/ainovel-cli`，仓库历史、许可证和上游署名都保留着。现在说的“自己的引擎”，是指当前运行时已经由仓库内代码替换，不是把整个 Git 历史说成从零原创。

第二件，是加了一个“授权语料校准”。

我自己长期写东西时最烦的一点，是所谓“去 AI 味”“更像网文”的提示词通常都很虚。于是现在可以导入自己有权分析的 TXT、Markdown 或 DOCX，让程序先看真实文本的段落长短、句长变化、对话比例、标点习惯、短段密度、解释性连接词和机械重复，再给指定 Prompt Skill 生成一份修改候选。

它不是训练模型，也没有“模仿某某作者”这个功能。导入的正文只在这次分析的内存里存在，最后留下的是 SHA-256、样本量、聚合指标和规则候选，不保存原文；来源作品的专名、情节和句子也不准进入提示词。候选要自己点确认才会应用，而且能一键退回应用前版本。

Pages 和自部署的处理方式也分开了：

- Pages 直接在浏览器里分析，原文不上传；
- Docker / 本地版交给自己的 Go 服务分析，档案落在 `.writing-workshop/corpus/index.json`，同样没有原文；
- 完整项目备份升到 v6，能带走语料统计和校准历史，但不带语料正文。

想先看看页面，不安装东西：

<https://zizegak916-glitch.github.io/writing-workshop/>

打开工作台后可以这样跑一遍：

1. 顶部 `＋` 新建项目，或者从项目操作台导入 TXT / Markdown / DOCX。
2. 进“流程”，普通润色就直接选功能；想校准提示词就打开“授权语料校准”。
3. 选文件并勾选“我有权分析这些文本”，看完统计再选要修改的 Prompt Skill。
4. 生成候选，先看差分，不满意就不应用；应用后也可以撤销。
5. 需要调用模型时到“设置 → API”，填写协议、Base URL、模型和 Key，先测试再保存。
6. 选正文和需要的项目上下文生成，结果会先到候选区；确认后才能替换、插入、追加或整理成记忆。
7. 写到一个阶段就导出 v6 项目包。Pages 数据在浏览器里，清站点数据之前一定先备份。

Pages 的自定义 API 现在是浏览器 BYOK，不会再拿配置去 POST 静态 `/api/config`，所以保存动作不该出现 405。不过目标接口仍然要允许 CORS；有些中转或本地 Ollama 不放行浏览器跨域，就得用下面的自部署版。

```bash
git clone https://github.com/zizegak916-glitch/writing-workshop.git
cd writing-workshop
docker compose up --build
```

然后打开：

```text
工作台：http://127.0.0.1:8080/app.html
本地服务控制台：http://127.0.0.1:8080/admin.html
健康检查：http://127.0.0.1:8080/api/health
```

第一次可以无 Key 启动，先试项目、导入导出和语料校准；要生成时再配置模型。服务默认只监听 `127.0.0.1`，现在还没有账号系统，别把 8080 直接裸到公网。

目前还有几件事没有装成已经完成：第三方 Skill 沙箱还没做，浏览器项目和后端项目也没有自动双向同步；四种模型协议现在主要靠本地模拟接口测试，不能代表所有中转都跑过；原生 CLI 的模型输出目前还是最后一次性给文本块，真正的 SSE/NDJSON 增量主要在 Web 路径。

我现在更想知道这个最小闭环到底会不会丢东西：建/导入项目 → 选上下文 → 生成候选 → 确认写入 → 恢复 → 导出备份。愿意试的佬友如果遇到问题，给系统、浏览器、版本、复现步骤和脱敏报错就行，不用发自己的私稿。

如果有人手里正好有自己有权处理的网文样本，也欢迎专门看看语料校准出来的规则是有用，还是只会把统计数字换一种说法。这部分我现在最缺的就是外部反馈。
